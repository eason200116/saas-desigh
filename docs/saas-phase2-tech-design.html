一、基础概念

先把2.0绕不开的几个核心概念讲清楚，后面的字段与流程都建立在这上面。结合二期 PRD（会员管理深度迁移与归因体系）。

1.1 多商户：一查询 + 两配置（能力地图）

一个总控后台管很多商户站点，所以同一功能要回答两个问题——「现在看/管哪个（些）商户？」（数据维度）和 「一套参数怎么省力铺给一堆商户？」（配置维度）。原型用三种形态解决：

1.2 归因体系：会员"从哪儿来"

归因 = 在会员注册那一刻，按优先级判定其首个命中的来源，写入会员档案并固化不再变更。解决运营/代理「这个会员是谁带来的、从哪个渠道来的」。共 4 大归因类型（广告投放 / 邀请来源 / 官方直推 / 自然流量）× 21 种枚举情况，详见第二章。

1.3 推广闭环 + 代理体系

推广闭环

「域名 → 渠道 → 推广 → 获客归因」：投放域名/渠道带参 → 用户点击进入 → 注册时采集参数 → 判定归因。本期开放 渠道管理 / 域名管理〔待定〕 / 防封救援〔待定〕 / 解析检测〔待定〕 四页承载前半段（后三页暂未定稿、研发请暂缓，以后续确认为准）。

代理体系

会员可绑定上级代理，形成最深 10 级代理树。收益方式分 返佣 / 返利两种佣金模式；返佣等级 Lv0–Lv8，支持「对上级返佣」「领取返佣」两个行内开关控制结算口径。

设备 / 指纹

同一自然人可能多账号。用 设备号（App 端稳定 ID）+ 浏览器指纹（H5 端）+ IP 三类标识做关联，派生「同IP/同设备/同指纹 注册数·登录数」，供风控下钻。

1.4 埋点采集口径

归因判定依赖 5 类埋点：激活 / 注册 / 登录 / 首充 / 付费。注册时点采集 来源参数（广告点击ID/UTM/Referrer/邀请码）+ 设备环境（设备号/指纹/IP/包名/版本），判定后落库固化。设备维度按终端二选一：App 端有设备号、H5 端有指纹，不堆两行。

归因如何判定、判定结果如何落库、21 种情况如何穷举。

2.1 优先级与判定规则

① 广告投放› ② 邀请来源› ③ 官方直推› ④ 自然流量

注册时按上述优先级从高到低取首个命中的来源作为「主归因」，写入档案后固化不再变更。例：既有广告点击ID 又填了有效邀请码 → 命中更高优先级「广告投放（裂变）」，邀请码作辅证保留绑定关系。

2.2 五类来源简介与举例

主归因往下细分为 5 类来源（在 2.1 的 4 类判定基础上补「未知来源」兜底）。来源出处：《集团核心层级 · 归因来源》§4。

主归因来源简介举例
自然流量无明确推广参数的直接访问或搜索进入，是每个商户必备的兜底来源。用户在搜索引擎搜商户名点进官网。
广告投放来自广告链接、UTM、媒体买量、落地页 campaign，用于核算投放效果与 ROI。Facebook 广告带 fbclid 进入落地页。

邀请来源由玩家、邀请人或外部代理的邀请码 / 链接带来，同时形成代理树。再分三类：正常邀请＝个人邀请；转盘活动邀请＝分享邀请转盘裂变；邀请任务＝完成邀请任务拉新。老玩家分享带自己 ID 的邀请链接（正常邀请）；分享「邀请转盘」拉新（转盘活动邀请）；完成「邀请任务」拉新（邀请任务）。
未知来源参数缺失、失效、过期、跨商户或无法识别 referrer，应可追踪失败原因。链接过期后直接打开域名。
