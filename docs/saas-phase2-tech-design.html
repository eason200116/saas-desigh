一、基础概念

先把2.0绕不开的几个核心概念讲清楚，后面的字段与流程都建立在这上面。结合二期 PRD（会员管理深度迁移与归因体系）。

1.1 多商户：一查询 + 两配置（能力地图）

一个总控后台管很多商户站点，所以同一功能要回答两个问题——「现在看/管哪个（些）商户？」（数据维度）和 「一套参数怎么省力铺给一堆商户？」（配置维度）。原型用三种形态解决：

多商户 · 一个总控管多站点
📊 数据维度（看）现在看 / 管哪些商户
①分数据查询
一屏看 一个 / 多个 / 全部 商户的数据
控件 MerchantFilterSelect
多选 + 全部 + 互斥
用于：会员 / 运营 / 报表 / 风控 列表
⚙️ 配置维度（设）一套参数怎么省力铺给一堆商户
②模板化配置
一套配置铺给一批商户、互相复制
载体 配置工作区
模板画廊 + 套用/复制 + 按商户分库
用于：VIP配置、返佣配置
③单站点配置
一次只配一个商户自己那套
控件 MerchantSwitchBar
单选切换
用于：注册管理 / 语言 / 系统参数 / 配置开关
详见《二期 PRD》第 12 节「多商户能力地图」与 V3《改动清单》同名章节。本技术方案聚焦 ① 分数据查询所依赖的会员归因字段。

1.2 归因体系：会员"从哪儿来"

归因 = 在会员注册那一刻，按优先级判定其首个命中的来源，写入会员档案并固化不再变更。解决运营/代理「这个会员是谁带来的、从哪个渠道来的」。共 4 大归因类型（广告投放 / 邀请来源 / 官方直推 / 自然流量）× 21 种枚举情况，详见第二章。

1.3 推广闭环 + 代理体系

推广闭环

「域名 → 渠道 → 推广 → 获客归因」：投放域名/渠道带参 → 用户点击进入 → 注册时采集参数 → 判定归因。本期开放 渠道管理 / 域名管理〔待定〕 / 防封救援〔待定〕 / 解析检测〔待定〕 四页承载前半段（后三页暂未定稿、研发请暂缓，以后续确认为准）。

代理体系

会员可绑定上级代理，形成最深 10 级代理树。收益方式分 返佣 / 返利两种佣金模式；返佣等级 Lv0–Lv8，支持「对上级返佣」「领取返佣」两个行内开关控制结算口径。

设备 / 指纹

同一自然人可能多账号。用 设备号（App 端稳定 ID）+ 浏览器指纹（H5 端）+ IP 三类标识做关联，派生「同IP/同设备/同指纹 注册数·登录数」，供风控下钻。

1.4 埋点采集口径

归因判定依赖 5 类埋点：激活 / 注册 / 登录 / 首充 / 付费。注册时点采集 来源参数（广告点击ID/UTM/Referrer/邀请码）+ 设备环境（设备号/指纹/IP/包名/版本），判定后落库固化。设备维度按终端二选一：App 端有设备号、H5 端有指纹，不堆两行。

二、归因流程图与介绍（含矩阵）

归因如何判定、判定结果如何落库、21 种情况如何穷举。

2.1 优先级与判定规则

① 广告投放› ② 邀请来源› ③ 官方直推› ④ 自然流量

注册时按上述优先级从高到低取首个命中的来源作为「主归因」，写入档案后固化不再变更。例：既有广告点击ID 又填了有效邀请码 → 命中更高优先级「广告投放（裂变）」，邀请码作辅证保留绑定关系。

2.2 五类来源简介与举例

主归因往下细分为 5 类来源（在 2.1 的 4 类判定基础上补「未知来源」兜底）。来源出处：《集团核心层级 · 归因来源》§4。

主归因来源简介举例
自然流量无明确推广参数的直接访问或搜索进入，是每个商户必备的兜底来源。用户在搜索引擎搜商户名点进官网。
广告投放来自广告链接、UTM、媒体买量、落地页 campaign，用于核算投放效果与 ROI。Facebook 广告带 fbclid 进入落地页。
官方直推商户运营创建的官方推广入口。线下活动二维码、KOL 专属短链、商务直推链接、活动落地页。
邀请来源由玩家、邀请人或外部代理的邀请码 / 链接带来，同时形成代理树。再分三类：正常邀请＝个人邀请；转盘活动邀请＝分享邀请转盘裂变；邀请任务＝完成邀请任务拉新。老玩家分享带自己 ID 的邀请链接（正常邀请）；分享「邀请转盘」拉新（转盘活动邀请）；完成「邀请任务」拉新（邀请任务）。
未知来源参数缺失、失效、过期、跨商户或无法识别 referrer，应可追踪失败原因。链接过期后直接打开域名。

2.3 各来源的入口与采集方式

每类主归因对应的入口形态，以及注册时如何采集 / 识别。

主归因入口形态采集 / 识别方式与举例
自然流量搜索进入 / 直接访问解析请求 referrer 的来源域名识别搜索引擎名称，无 referrer 则记为直接访问。覆盖海外主流：Google、Bing、Yahoo、DuckDuckGo、Yandex、Naver、Daum、Ecosia、Brave Search、Startpage、Qwant、Seznam、Ask.com、AOL 等；国内引擎（百度 / 搜狗 / 360 / 神马 / 头条等）及未在白名单内的搜索引擎一律归「其他」。
广告投放广告链接 / 落地页读取 UTM 参数（utm_source / utm_medium / utm_campaign / utm_content / utm_term）+ 各平台点击 ID 回传。暂定支持 4 个广告平台系列：
• 谷歌系列：Google Ads / YouTube / Google Display（含 AdMob 应用广告），点击 ID gclid（iOS ATT 后另有 gbraid / wbraid），utm_source=google。开发文档：Google Ads API。
• Meta 系列：Facebook / Instagram / Messenger / Audience Network，点击 ID fbclid，utm_source=facebook 或 instagram。开发文档：Meta Marketing API。
• TikTok 系列：TikTok Ads / TikTok for Business，点击 ID ttclid，utm_source=tiktok。开发文档：TikTok Marketing API。
• Kwai 系列（快手海外版）：Kwai Ads / Kwai for Business，utm_source=kwai，点击 ID 随平台回传（参数名以对接 Kwai SDK 为准）。开发文档：Kwai Business API。
例：?utm_source=facebook&utm_campaign=th_618。
官方直推专属链接 / 二维码商户在「官方直推渠道」生成带渠道标识的短链或二维码，扫码 / 点击即带上渠道 ID。例：线下展会物料二维码、KOL 专属 ?ch=kol_anna。
邀请来源 · 正常邀请个人邀请码 / 邀请链接链接或邀请码内含上级玩家 / 代理 ID，注册时写入代理树上级关系，invite_type=normal。例：/r/INV8K3D 或填邀请码 8K3D。
邀请来源 · 转盘活动邀请邀请转盘专属链接 / 海报链接含上级 ID + 活动 ID，注册时既挂代理树又触发转盘奖励，invite_type=wheel 并记 invite_activity_id。例：/act/wheel?inv=8K3D&act=2026spin。
邀请来源 · 邀请任务邀请任务活动页 / 任务链接链接含上级 ID + 活动 ID，注册时既挂代理树又触发任务奖励，invite_type=task 并记 invite_activity_id。例：/act/task?inv=8K3D&act=2026invite。
未知来源兜底上述均无法识别时落入未知来源，记录失败原因（参数无效 / 过期 / 跨商户）。例：referrer 与 UTM 均为空且非已知直接入口。
优先级冲突：若邀请链接与 UTM 同时存在，按优先级判为广告投放（广告 / UTM 高于邀请），邀请链接作辅证保留；来源归因与代理树归属相互独立。来源出处：group-to-member-hierarchy.html#attribution §4。

三、通用交互 · 研发落地要点

归因之外，《交互介绍（控件级）》里还有一批贯穿全站的通用交互，研发实现时按本节口径落地，逐页不再重复。控件级细节以《交互介绍》为准，本节给技术锚点。

3.1 列表骨架（统一用 ProCrudTable）

所有列表页（搜索表单 + 表格 + 分页 + 行操作）统一走自研 ProCrudTable，不要各页另起一套。

  • 搜索：条件即时过滤；pin 项常驻、其余「展开/收起」；日期区间带快捷（今天/昨天/本周/上周/本月/上月/所有）。
  • 列：内容默认居中；状态/类型列渲染彩色 Tag；金额千分位；时间按商户时区展示；空值统一「-」。
  • 操作列：恒最后一列、默认右侧冻结（横/竖版都冻、不可取消），横向滚动始终可见。
  • 自定义列：列 >10 才出；勾选保存后才生效；锁定列 lockFixed 在面板内不可取消勾选 / 不可拖拽，仅显隐其它列；按 tableId 记忆（useColumnSetting）。
  • 分页：10/20/50/100，各页独立记忆；列表页 keepAlive 保留滚动与筛选态。
  • 合计行：含统计意义的列表带「本页合计 / 总计」，随筛选实时刷新。
  • 导出：仅「报表类页面」或「列数 >20」才提供，点击真实下载 CSV + Toast；其余列表不放（R21）。
  • 嵌套分组列（group columns） 2026-06-26 新增：底层表格 ProDataTable 的列规范化 processedColumns 原先逐列拍平、丢弃嵌套 children，导致两行分组表头失效（昨日返佣等级 5 游戏品类退化成 5 个单列、数据全显 -）。已抽出 buildLeafColumn（统一构造叶子列）并新增 normalizeNode 递归处理 children（纯新增分支、不改既有叶子列逻辑），支持父表头横跨多子列。修复后昨日返佣等级每个游戏品类作父表头横跨「有效投注流水 / 返佣金额」两子列、显示真实数据；pnpm build 通过，实测表头由 1 行变 2 行、父列 colspan=2。

3.2 配置类页 · 保存 / 发布两段式

注册管理 / 系统参数 / 配置开关 / 前台配置等配置页统一：

  • 两段式：保存 = 存草稿（先弹「保存预览」确认，提示「已保存（草稿），发布后对外生效」）；发布 = 上线（再走「确认发布」二次确认）。
  • 按钮位置：保存 / 发布放在顶部「配置商户」选择条同一行右侧（MerchantSwitchBar #actions 插槽）。
  • 板块级保存（系统参数 / 配置开关） 2026-06-26 调整：系统参数配置（/config-center/sysParam）与开关配置（/config-center/configSwitch）取消顶部全局「保存」按钮、顶部仅保留「发布」；改为每个板块/分组卡片各挂一个「保存」按钮——系统参数 8 个分类卡（注册与登录安全 / 资金与绑定 / 汇率 / 营销与奖励 / 代理 / 预警监控 / 下发限制 / 第三方与外观）各自标题栏一个「保存」，只校验并保存该板块（草稿，红框仅标该板块出错项）；开关配置 10 个分组卡各自卡头一个「保存」（点击不触发卡片折叠），只保存该分组（草稿）。「发布」仍为全局（各板块分别存草稿，顶部「发布」统一对外生效）。其余配置页（注册管理 / 前台配置等）保持顶部全局保存/发布不变。
  • 系统参数配置 / 开关配置 两页菜单隐藏 2026-06-26 调整：在路由 config.ts 给 sysParam（系统参数配置 /config-center/sysParam）、configSwitch（开关配置 /config-center/configSwitch）两条 meta 加 hidden:true，配置中心菜单不再展示这两页，但路由与组件保留、可直达（没删，只是菜单隐藏）；机制：菜单生成器 utils/tree.ts 按 meta.hidden 过滤。原因：这两页已被融合页「开关参数配置」取代。隐藏后配置中心大菜单现仅余 VIP配置 / 返佣配置 / 消息模板配置 / 开关参数配置 / 注册管理 / 前台配置。
  • 共用侧导航「配置项·快捷入口」模糊搜索（增强：页面入口 + 跨页配置项名） 2026-06-26 增强：共用左侧导航组件 ConfigSideNav（覆盖 VIP配置 / 返佣配置 / 消息模板配置 三页）仅展开态在「配置项·快捷入口」标题下方常驻一个搜索框（placeholder「搜索配置项…」、可清空）。实现为纯前端 computed 过滤，匹配范围有两类：①页面入口——按入口的标题 / 描述 / 短名 做 includes 子串匹配（不区分大小写，对应 VIP配置 / 返佣配置 / 消息模板配置 三个入口）；②跨页配置项名称——新增索引文件 src/views/config/shared/configSearchIndex.ts，收录 VIP配置 19 项（等级表列 + 经验值）+ 返佣配置 17 项（等级条件 + 费率）+ 消息模板 12 个推送场景名，共 48 项，用户可直接搜某个具体配置项名（如「升级奖励」「洗码」「会员注册」）。结果列表每条带一个彩色标签：蓝色「页面」/ 紫色「配置项」，右侧主标题=命中名、副标题=所属页名；点任意结果都跳转到其所属配置页（页面入口跳该页，配置项跳所属页）。无命中显示「无匹配配置项」。收起态（左侧短标签竖排）不受影响。参照「开关参数配置」(switchParam) 页内目录搜索做法；pnpm build 通过，Playwright 实测：「返佣」→ 页面「返佣配置」+ 配置项「返佣等级/返佣费率配置」，「升级」→「升级条件(EXP)/升级奖励」，「会员注册」→ 消息模板场景，「洗码」→ 5 个洗码率列，无关词 → 「无匹配配置项」。

3.3 弹窗规范（全站统一）

3.6 多语言文案 · 逐语言维护落地口径 2026-06-25 新增

四、VIP / 返佣配置 · 逻辑与边界

📌 基本规则：无论模版复用、复制商户还是自定义配置，某商户的生效配置一律以「最新一次保存 / 发布」为准——三种来源只是初始化来路（写一次 source 标记），落库后即成为该商户自己的独立数据；之后对该商户的任何改动覆盖旧值，不回溯、不联动原模板 / 原商户（反之改模板 / 改源商户也不影响已套用 / 已复制的商户）。

4.2 VIP 配置逻辑

  • 子页签：VIP 等级配置 / 经验值配置。
  • 等级表：固定 11 级 VIP0–VIP10，名称只读、不可增删；结算日只读；其余 14 个数值列行内常驻可编辑（InlineNumberCell）。
  • 步长分档：经验 / 赠送上限 / 提现次数等 step=1；充值奖励、五游戏洗码率 step=0.01。

4.3 返佣配置逻辑

  • 子页签：返佣等级管理 / 返佣费率配置。
  • 等级管理：行内新增（lv = 现有最大 + 1，新行置顶）/ 编辑 / 删除（二次确认）；L0 基础等级不可编辑 / 删除（操作列灰字「基础」）。团队条件（充值人数 / 充值金额 / 有效投注流水）与直属条件各带只读「满足人数」占位列（配置态恒为 0，运行时统计）。
  • 费率配置：按等级卡片排列，每卡 = 行 6 层级（tier1–tier6）× 列 5 游戏大类（彩票 / 电子 / 真人 / 体育 / 棋牌），逐格 6 位小数（step=0.000001），卡内编辑 / 确认 / 取消。
  • 核心校验（≤5%）：每个游戏大类「跨 1–6 级纵向求和 ≤ 5%」（对齐源站 RebateLvRateConfig；判定用 > 5.000001 留浮点容差）。越限 → 该游戏整列标红 + 单元格 errorTip + 顶部 message 指名「游戏（合计 x%）」，拦截不保存；通过后费率四舍五入到 6 位小数落库。

5.4 配置工作区 · VIP / 返佣 / 消息模板（模板化套用）

三者共用同一套「模板套用 / 保存草稿 / 发布 / 复制商户」状态机（§4.1）。建议配置模板表 + 商户配置发布表两张通用表承载，config_type 区分 vip / rebate / msg，payload 用 JSON 存整套配置，避免为每类配置单独建宽表。
