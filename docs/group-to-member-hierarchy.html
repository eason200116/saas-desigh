本文为「集团 → 市场 → 商户 → 域名 → 渠道 → 会员」层级树状图提供配套说明， 只解释层级关系本身，不展开字段、接口、表结构与异常状态机。

§0 文档定位

本文档分为「核心层级」与「核心体系」两部分。核心层级自上而下讲清 集团 → 市场 → 商户 → 域名 → 渠道 → 会员 这条主线上每一层的含义、归属关系，以及层级之间的继承、授权与入口关系（§1–§3）。

核心体系包含两大主类型：归因来源（§4）解释会员最初从哪个入口来、如何按优先级判定主归因并逐层归集到集团； 代理体系（§5）解释会员之间的推广关系、代理树归属与返佣 / 盈亏两种代理模式。

文档只解释层级与体系的关系本身，不展开字段、接口、表结构与异常状态机。前置原则： 端是访问入口，不是业务层级——平台端、商户端、代理端、会员端只是不同身份进入同一套业务体系的窗口。

实线 = 从属主线

集团 → 市场 → 商户 → 域名 → 渠道 → 会员。上一层确定下一层的归属边界，逐层向下、不跨层混用。

虚线 = 继承 / 授权 / 入口关系

市场模板向商户「默认继承」配置；商户团队「按授权经营」域名与渠道；四端只作「身份入口」接入对应层级，不构成业务层级。

主线口径一句话：集团下分市场，市场下挂商户，商户持有域名，域名承载渠道， 渠道按来源分为投放、代理、自流量三类，三类渠道最终都把流量沉淀为会员； 市场模板默认继承、商户团队按授权经营、四端作身份入口，是挂在主线上的横向关系。

§1.1 层级间关键关系

市场模板 · 默认继承

市场以国家为唯一键，由平台提供默认配置参数（金额、支付、风控阈值、VIP 档位、本地化）。商户启用后默认继承，可在自身范围内调整；平台后续变更不自动覆盖已启用的市场模板。

商户团队 · 按授权经营

商户用一支职能团队经营旗下业务。账号能力由角色配置决定，可操作范围由权限配置决定；团队对域名、渠道、会员的操作都在授权边界内进行。

域名类型 · 入口资产

一个商户可拥有主站、推广、落地、备用域名。域名负责把访问落到确定的商户上下文；解绑、换绑或停用只影响后续解析，不改写历史快照。

代理树 · 推广关系

会员之间天然可形成邀请 / 推广关系，构成代理树。代理类渠道在带来会员的同时形成推广关系；代理树服务于下线查看、佣金计算与代理报表，与渠道来源归因相互独立。

四端入口：平台端接入集团级上下文，商户端接入商户团队（商户上下文），会员端接入单个会员上下文， 代理端只读查看自己的代理线。端是访问入口，不是业务层级。

§2 各层级说明

集团

最高归属与控制方，统管旗下多个市场与商户，负责整体策略、资源调配和全局口径，是整条链路的顶层边界。

市场

按国家或地区划分的经营单位，承载币种、语言与本地化口径，使各市场的金额、风控阈值、活动档位互不混用。以市场模板（国家为单位、币种与语言为属性）向下默认继承给商户。

商户

实际的运营主体与合同、计费、团队归属边界，是会员与业务数据的隔离边界。其下挂商户团队（角色配置 + 权限管理），按授权经营域名、渠道与会员，是经营责任的承载层。

域名

商户级入口资产，分主站、推广、落地、备用等类型，负责把访问落到确定的商户上下文。域名先定上下文，渠道再定来源；域名不归属于渠道，渠道启停或删除不改变域名归属，也不改写历史会员来源。

渠道

挂在域名之下的「来源归因容器」，用于统计与运营管理。渠道可绑定本商户下已配置、可用的域名生成推广入口，但不能跨商户借用域名。详见 §3。

会员

面向 C 端的玩家主体，是注册、钱包、投注、活动、VIP、邀请关系的承载者。会员之间形成代理树（邀请 / 推广关系）。会员严格按商户隔离，钱包、订单、VIP、佣金与客服记录都不跨商户混用。

数据模型 · 层级基数（研发）

建表前先对齐各层从属的基数，避免外键挂错层：

关系基数说明
集团 → 市场1 : N一个集团下多个市场（按国家 / 区域划分）
市场 → 商户1 : N商户归属单一市场（主运营市场）；若需经营其它市场 / 币种，在对应市场下另建商户，不跨市场混用。商户（merchant_id）是会员与业务数据的隔离边界
商户 → 域名1 : N主站 / 推广 / 落地 / 备用；域名是商户级入口资产
域名 → 渠道1 : N一个域名下可挂多个推广渠道；渠道绑定所属域名生成推广入口
渠道 → 会员1 : N一个推广渠道下可注册多个会员；会员注册时落到唯一渠道（来源归因）
会员 ↔ 会员（代理树）自关联 · ≤ 10 级上下级推广关系，单一直接上级，最高 10 级
数据规则：①会员唯一键 UNIQUE(merchant_id, login_name)，同一手机号 / 邮箱可在不同商户各自注册为独立会员； ②钱包 / 订单 / 投注 / 活动 / VIP / 佣金均以 merchant_id 为隔离键，不跨商户混加； ③商户固定单一经营币种，继承所属市场模板；不同币种不做汇率折算直接相加。

§3 渠道三分类（来源归因）

渠道层把会员的来源拆成三类。它回答「会员最初从哪个入口来」， 与「会员之间的推广关系（代理树）」以及「当前由哪个员工经营（业绩归集）」是三件独立的事， 同时存在但不混成同一个字段或同一个动作。

投放

付费广告来源。来自广告链接、UTM、媒体买量、落地页或广告 campaign，用于核算投放效果、ROI 和广告渠道质量。

代理

分销 / 推广来源。由会员、邀请人或外部代理的邀请码、邀请链接带来，既产生来源归因，又形成会员之间的推广关系。按发起形态分正常邀请（玩家 / 邀请人 / 代理发起的个人邀请）、转盘活动邀请（玩家分享邀请转盘拉新的裂变行为）与邀请任务（玩家完成邀请任务拉新）三类。外部代理本质是「会员 + 代理端只读查看能力」，代理本人不作为渠道本体存在。

自流量

自然 / 私域来源。无明确推广参数的直接访问，以及商户自建的官方直推入口（线下二维码、KOL 链接、活动落地页等）。每个商户必须有一个默认自然流量入口作兜底，不允许手工删除。

来源优先级（简化口径）：官方直推 → 广告 / UTM → 可识别自然访问 → 有效邀请链接 → 未知来源。 原始来源一旦在注册时固定，员工划拨、撤销代理端、渠道关闭都不改写。

§4 归因来源

归因来源回答「会员最初从哪个入口来」。 玩家访问商户入口后，域名先确定商户上下文，渠道与推广参数再确定来源， 注册完成时主归因即被固定，并保留 UTM、referrer、落地页、二维码等辅助证据。原始来源一旦写定， 员工划拨、撤销代理端、渠道关闭都不再改写。

从归因到集团的整体流程： 会员在某域名注册 → 系统按优先级判定主归因（官方直推 > 广告 > 自然 > 邀请 > 未知）→ 该会员的注册、投注、充值等流水带上「渠道 / 员工 / 代理树」三个维度 → 数据先在渠道内汇总（ROI、流量质量），再到域名 / 商户（经营责任、商户聚合）， 逐层向上到市场（按国家 / 币种口径），最终在集团形成全局报表。 每一层只在自己的边界内聚合，不同币种、不同市场不直接混加。

流程图 3 整体流程：玩家访问商户入口后，系统按固定优先级依次判定主归因，命中即停—— 第一个满足的条件即作为该玩家的主归因，不再向下判断。判定顺序为： 有效官方推广链接（→ 官方直推）→ 有效广告参数 / UTM（→ 广告投放）→ 可识别自然访问（→ 自然流量）→ 有效邀请链接（→ 邀请来源，同时建立代理树推广关系）→ 都不满足则归未知来源并保留失败原因。

判定完成后注册完成，主归因写入快照就此固定，员工划拨、撤销代理端、关闭渠道均不改写； 与此同时，该玩家后续的注册、投注、充值等流水按渠道 → 商户 → 市场 → 集团逐层三维归集。 核心原则是优先级唯一、命中即停、就高不就低（如官方推广链接与邀请链接同时存在，优先判为官方直推）。

邀请来源再细分为三类（invite_type）： 正常邀请——玩家、邀请人、代理等角色发起的个人邀请行为（个人邀请码 / 链接）； 转盘活动邀请——玩家通过分享邀请转盘活动拉新的裂变获客行为（活动专属邀请链接，带活动 ID）；邀请任务——玩家通过完成邀请任务活动拉新（带活动 ID）。 三类都进代理树、都归代理（上级），区别仅在发起形态与是否携带活动上下文： 正常邀请用于核算个人 / 代理拉新，活动邀请（转盘 / 任务）用于核算各活动裂变效果与 ROI，分开统计。

访问端（六类）

玩家访问入口的客户端类型在注册时记录为 client_type，与主归因正交（端只回答「从哪种客户端进来」，来源回答「从哪个入口来」）。共六类：

iOS 原生

上架 App Store 的原生 iOS 应用，原生壳 + 原生界面。例：从 App Store 下载的官方 App。

安卓原生

原生 Android 应用（APK），原生壳 + 原生界面。例：官网或应用市场下载的安卓 App。

iOS 壳包

iOS WebView 套壳应用，外壳为原生、内容为 H5。例：用套壳分发绕过审核的 iOS 包。

安卓壳包

Android WebView 套壳 APK，外壳为原生、内容为 H5。例：渠道分发的安卓套壳包。

PC 端（含平板）

桌面浏览器访问，含平板等大屏设备。例：Windows / Mac 浏览器或 iPad 横屏访问。

手机 H5 端

移动浏览器直接访问的 H5 页面，无需安装。例：手机浏览器打开推广短链。

五类来源简介与举例

自然流量

无明确推广参数的直接访问或搜索进入，是每个商户必备的兜底来源。例：用户在搜索引擎搜商户名点进官网。

广告投放

来自广告链接、UTM、媒体买量、落地页 campaign，用于核算投放效果与 ROI。例：Facebook 广告带 fbclid 进入落地页。

官方直推

商户运营创建的官方推广入口。例：线下活动二维码、KOL 专属短链、商务直推链接、活动落地页。

邀请来源

由玩家、邀请人或外部代理的邀请码 / 链接带来，同时形成代理树。再分三类：正常邀请＝玩家 / 邀请人 / 代理发起的个人邀请；转盘活动邀请＝玩家分享邀请转盘活动拉新的裂变行为；邀请任务＝玩家完成邀请任务活动拉新。例：老玩家分享带自己 ID 的邀请链接（正常邀请）；玩家分享「邀请转盘」活动拉新（转盘活动邀请）；玩家完成「邀请任务」拉新（邀请任务）。

未知来源

参数缺失、失效、过期、跨商户或无法识别 referrer，应可追踪失败原因。例：链接过期后直接打开域名。

归因边界与边缘情况（研发）

邀请 + UTM 同时存在

按优先级广告 / UTM 先于邀请命中，主归因判为广告投放，邀请链接作为辅助证据保留；是否归上级代理由代理树绑定规则单独判定（来源归因与代理树归属相互独立）。

多次触点

归因窗口内末次触点定来源；代理绑定以首次为准，不被后续覆盖。

跨商户邀请码

在 B 商户使用 A 商户的邀请码 / 链接无效（商户隔离）→ 落未知来源，记录失败原因。

referrer / UA 被抹除

隐私模式、Tor、部分 App 内置浏览器会抹除 referrer 与精简 UA → 无法判搜索引擎，归自然流量直接访问或未知来源。

防作弊 / 防环

自己邀请自己、上下级成环、同设备多账号需校验拦截，不写入代理树。

移动端归因（注明）

本期以 web 的 referrer / UTM / 点击 ID 为准；App 安装归因（deep link、deferred deep link、设备指纹匹配）另行设计。

来源归因 · 代理树归属

主归因是否进代理树玩家归属说明与举例

§5 代理体系

代理体系回答的是「玩家之间的推广关系是什么」， 而不是「玩家从哪个渠道来」。外部代理的本质是「玩家 + 代理端只读查看能力」—— 升级外部代理只是为该玩家增加一个代理端账号和只读权限，不改变其玩家身份。

每个玩家天然可以拥有邀请关系或推广链；代理树描述玩家之间的上下级关系， 服务于下线查看、推广关系、佣金计算和代理报表。撤销外部代理只关闭代理端入口与查看能力， 玩家端账号、历史下线、原始来源和历史佣金事实都不变。

代理树写入约束（研发）：每个会员只有一个直接上级；写入时须防环校验—— 自己不能成为自己的上级，也不可形成上下级闭环；代理树最高 10 级。

归属判定只看注册时是否绑定代理关系：无绑定 → 归属平台（自然、广告、未知、未绑代理的官方直推）；有绑定 → 归属代理（邀请来源、绑定了代理的官方直推），挂入上级代理线。代理树最高 10 级。

代理层级（1–10 级）

代理层级指代理树中从某代理到其某个下线之间的层级距离：某代理的直接下线为其 1 级下线，下线的下线为 2 级，依此类推，最深至 10 级。 同一会员只有一个直接上级，整条上级链路记录在 agent_path 中。

层级用于多级分润的级差计算、下线列表与代理报表的层级展示。 例：A → B → C，对 A 而言 B 是 1 级、C 是 2 级；按级差制，A 在 C 的业绩上实得「A 级比例 − B 级比例」的部分。

代理端可见

下线昵称、注册时间、VIP、渠道、脱敏联系方式，下线的充值 / 提现 / 投注 / 派彩流水，自己的佣金报表与推广素材库。

代理端不可见

下线密码、完整敏感身份资料、设备指纹、登录历史、后台风控判断、商户内部备注与员工经营归属。代理端只读，不能改资料、动资金、管渠道。

两种代理模式

返佣代理模式（投注流水返佣）

按下线的投注流水（turnover）固定比例返佣，无论玩家输赢都产生。成本可预测、激励走量。
例：下线本月投注流水 100,000，返佣比例 0.8% → 代理获 800。

盈亏代理模式（用户亏损返利）

按下线净亏损（即平台净盈利）的一定比例分成；下线整体盈利时本期分成计 0 或负数结转。与平台盈亏挂钩、高风险高回报。
例：下线本月净亏损 50,000，分成比例 30% → 代理获 15,000；若该月下线整体盈利，则代理分成为 0。

对比维度返佣代理模式盈亏代理模式
计算基数下线投注流水下线净亏损（平台盈利）
是否随输赢波动否，按流水稳定结算是，玩家赢则无分成
代理收益特征稳定、可预测波动大、上限高
平台成本特征固定成本，走量越大越高与盈利同向，亏损时不付
适合代理类型大流量、低净亏的拉新型高净值、高亏损的深耕型
两种模式都只改变佣金如何计算，不改变代理树结构与来源归因。核心原则：不提供转代，不通过运营动作重排代理树；员工间划拨只改经营归属，不改原始来源与代理树位置。

项目定义 / 规则

调整与冲减撤单、红包冲回、风控扣回在结算前并入基数，避免多发或漏扣。

§6 关键原则

  1. 逐层从属，不跨层混用。上一层确定下一层的归属边界；会员、资金、订单等关键数据以商户为隔离边界。
  2. 域名定上下文，渠道定来源。只有域名而无明确渠道信息时，进入该商户的默认自然流量入口。
  3. 三套关系分离。来源归因（渠道）解释入口，代理体系解释会员之间的推广关系，业绩归集解释当前员工的经营责任，三者不可合一。
  4. 历史事实不被改写。注册时的市场、商户、域名、渠道与来源会形成快照，后续配置调整、划拨、渠道关闭均不反向改写历史。
  5. 不提供转代。不通过运营动作重排会员之间的代理树；员工间划拨只改经营归属，不改原始来源与代理树位置。
